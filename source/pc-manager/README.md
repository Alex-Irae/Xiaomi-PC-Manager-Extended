# PC Manager

This component is part of Xiaomi Revamp 0.2.0. Its released source, shared shortcuts, data paths and installer are documented in the [parent PC Manager README](../../README.md). Use the app's `Development/Launch.cmd` to rebuild and run edits with copied offline dependencies. The remaining notes document the standalone baseline and its original developer workflow.

This copy is the suite edition. Use the [suite README](../../README.md) for installation, build and data paths. Its deployed entry point is `install/PC Manager/PCManager.exe --manager`, with isolated suite settings. PC Manager owns optional app shortcuts while running; Keyboard exposes shared bindings and Toolbox exposes launch/status and optional theme/accent sharing. When it exits, running optional apps resume their own shortcuts. The suite's default Copilot action releases the chord for Screen Translator. The component documentation below retains baseline behavior and historical paths; its original setup/deployment scripts are not the suite installer.

An English Windows tray resident with a small white Xiaomi-style quick panel, a larger categorized manager, and the original XiControl hardware monitor. It reuses the supplied XiControl 0.16.0 firmware, display, input and policy code in process. It does not run a XiControl executable. The original Xiaomi English-patched package and supplied XiControl codebase remain unchanged.

## Main interface

A confirmed brightness shortcut updates the visible quick-panel slider directly, without waiting for its next full device-state refresh.

The quick panel contains brightness, current-source performance modes, Travel charge / Cancel travel, up to eight selected system controls, up to four app/file/folder links, then explicit Xiaomi driver/tools access at the bottom. The default system controls are Screen off, Stay awake, manual Hz, automatic Hz, touchpad, touchscreen, Monitor and Prevent sleep; Settings can exchange these for Calculator, Notepad, Screenshot, Clipboard or Project and move the selected controls up or down. Prevent sleep creates process-scoped Windows system and background-execution requests without keeping the OLED display on. It defaults off, remembers the choice across resident starts, and reissues its requests after resume and AC reconnection. On AC these requests can keep desktop work running after display-off. On this Modern Standby laptop, Windows can end them on battery about five minutes after the sleep timeout. The user's heartbeat logs show that a desktop process stopped in one AC session, continued through a separate 28-minute AC screen-off session, then stopped immediately when the earlier Screen off command was used. See the runtime report for exact event times and the replacement Screen off test. Neither Screen off nor Prevent sleep guarantees a long battery compile with the physical display off. Explicit Sleep and lid-close rules still apply. Stay awake is the separate XiControl control and may also hold the display on, depending on its display option. Screen off is a one-time physical display-off request. Its charging estimate is a compact number of minutes. Persistent charge-limit selection is available only in the larger manager's Battery page. Sharing, Device Center and the old utility row are absent.

The larger manager has This PC, Performance, Battery, Display, Touch and input, Keyboard, Notifications, Monitor, Toolbox and Settings. These categories use this app's own English UI with XiControl controller callbacks and guards. There are no separate Advanced / More settings destinations. The header searches setting names, descriptions and a small set of related terms; its Store bag opens the optional standalone Xiaomi Store. The header Refresh reconnects the proprietary firmware client and reloads device readings without closing the manager. This PC shows the Windows device name, model, BIOS, current power source, capacity, charging-time estimate, processor, graphics, memory modules, storage, volumes, network adapters, Windows version and mainboard. WMI inventory is cached once outside the fast control path. Unreported fields remain unavailable. Device names also appear in the quick panel. Its Home button opens This PC; Refresh sits beside it and reports when a device read completes. The bottom navigation/footer controls are removed. The quick panel is fixed-size and frameless; the manager retains native Windows frame styles for taskbar/minimize/maximize transitions while drawing its own borderless Xiaomi chrome and resize grips. Maximizing leaves a one-physical-pixel bottom activation strip for an auto-hide taskbar. It opens centered within the current screen work area and retains its resized dimensions while resident. Closing it returns to the tray and releases its WebView renderer to reduce background memory; reopening reconstructs the manager from cached device state. Its native taskbar entry can minimize the window; Settings offers an optional Minimize to tray toggle, off by default. Only its content column scrolls; the header and navigation stay visible, and changing tabs returns to the top.

Settings shows the effective accent, background and card colors for each built-in light/dark palette. Editing any picker immediately applies the change and switches the selection to Custom. Enter a name beside the selector and choose Save preset to keep the current three colors as one of up to 20 reusable named palettes. Select a saved palette to rename it or delete it; deleting the active palette retains its colors as Custom. Palette actions support the manager's undo and redo buttons. Palette data is stored in the daily `settings.json`; it is not exported to Xiaomi's original manager.

AC modes are Silent, Smart, Full speed and Eco. Battery modes are Eco, Quiet, Auto and Turbo. Confirmed choices are remembered separately and reapplied on source changes. Balanced cannot be selected. Silent/Quiet share firmware value 2; Smart/Auto share value 9. Full speed is 4, Eco is 10 and Turbo is 3. Unknown or unsupported modes remain unavailable.

Performance, lock, backlight, microphone, touchpad, touchscreen and display-rate OSDs use supplied English Xiaomi artwork in this process, without launching Xiaomi's OSD utility. Connecting or disconnecting AC shows a battery card from local Xiaomi artwork. If automatic refresh rate changes while that card remains visible and within 2.2 seconds, the rate card appears beside it rather than replacing it; other near-simultaneous Xiaomi-style cards use the same two-card layout. The OSD window is slightly translucent. Travel and Windows-key unlock use matching local SVG cards because the supplied package has no corresponding original artwork. Settings offers Xiaomi and XiControl OSD styles. The initial placement is lower center, with bottom clearance proportional to each OSD card's height: its center sits about 1.45 card heights above the working-area bottom. Notifications settings select position and duration for performance and other notices. Magenta transparency is absent. Test mode adds numbers 1 to 4 in current-source order. Preview buttons do not change hardware.

Keyboard settings use XiControl's MIFS event watcher, model key map, gesture timing and action router. Mi opens the quick panel, Settings/F9 opens Windows Settings, and AI/F7 opens the newest numeric-version XiaoAI installation under `C:/Program Files/MI/XiaoaiAgent`. F7 screenshot handling defaults off. Version-5 setup migrates the previous redundant/no-action AI defaults once, restores the built-in Home icon and retires rate-hold enforcement, while retaining other custom bindings. On laptops that emit the configured firmware events, Fn+K mode changes are read and remembered without a second firmware write, and the refresh-rate event cycles enabled supported rates. Physical Fn+K/Fn+S behavior remains unverified on this TM2424; the current capture contains no events and does not establish that the combinations were pressed.

Keyboard also offers up to 16 custom Windows shortcuts using Ctrl, Alt, Shift or Win plus a key. Actions include any manager page, device actions, XiaoAI and saved links. Choose an application from the action dropdown; cancelling the file picker retains the previous mapping. The selected link appears in the quick panel if fewer than four links are already visible; otherwise it remains available for keyboard mappings and can be shown by replacing one of those four in Settings. Fn is handled by firmware and is not a RegisterHotKey modifier; Windows-reserved or conflicting chords are refused. Native `.exe` selection for firmware keys remains independent of popup links. Commands and selected links run through the normal Explorer desktop broker. Physical event delivery and app-launch compatibility remain model-specific. Test mode disables firmware-key routing.

The optional Copilot key has a separate action selector in Keyboard settings, including app selection inside its dropdown. The default Do nothing intercepts Win+Shift+F23 in the resident so Windows Settings does not open; Windows default releases the chord back to Windows. It can also open a manager page, control, or selected app. This is a reversible in-process low-level keyboard hook, not a registry remap, and it stops when the resident exits. The keyboard page counts matching presses for diagnosis. The physical Copilot key on this laptop was observed to increment that counter while Windows Settings stayed closed. Hardware that emits a different signal is not supported until its event is identified.

Every editable category has a Reset category to defaults button and puts default values inside short `?` help tooltips, rather than below every setting. Resets invoke the same control callbacks and report partial failures. Performance resets to Smart/Auto source profiles; battery resets to 80% with travel off; display resets to 50%, its lowest supported rate and automatic policies off; input resets to enabled with Medium haptics and Standard force. Settings resets restore Xiaomi OSD style while retaining the profile picture, saved app links, selected OEM executable and API token and disabling API access. Keyboard reset clears custom Windows shortcuts and suppresses the Copilot chord as well as restoring firmware mappings. Appearance changes immediately apply to both windows and the native monitor, with Light, Dark and Follow Windows options. AC and battery ambient-light curve points have a live logarithmic-lux graph beside their editor. Blue, red, pink and green accent presets and custom accent/background/card colors are available. Everyday mode hides routine success/debug messages and API controls; Developer mode reveals them. Actual control errors remain visible.

Input switches apply without confirmation. App-owned disables are restored at the next resident start by default. Touch and input offers separate keep-disabled-after-restart toggles; these retain app-owned disables, including reapplying a soft disable after Windows re-enables the node. Devices disabled outside this app are not claimed or automatically enabled.

Settings also allows popup position and offsets, scale from 75% to 110% (85% default), compact layout, built-in icon selection, selection and ordering of up to eight system controls, and ordered links to local apps, files or folders. Selected controls appear first in the editor; Move up/down changes their order immediately in the quick panel. At most four saved links show in the quick panel; other links can still serve keyboard shortcuts. The icon disclosure stays open across state refreshes and selections; tab changes and its chevron close it. Native pickers choose files/folders, PNG icons and a separate profile picture. Profile pictures are cropped to a 256-pixel PNG and replace the panel logos, leaving the native taskbar/tray icon unchanged. Without a selected picture the app logo remains. Previously copied pictures are retained when resetting the profile. Translation and file-search integrations are separate unfinished projects.

## Program flow and structure

`Tray / fixed command / firmware key -> resident -> trusted local WebView or native monitor -> XiControl / Windows handler -> verified device state -> UI and local OSD`

- `Program.cs`: fixed CLI commands, single daily/test hardware owner and privilege bootstrap.
- `ManagerApplication.cs`: tray, windows, basic/advanced readiness, startup isolation and policy lifetime.
- `MainWindow.cs`: local WebView2 hosting, popup placement, typed command routing, visibility/suspension and validation hooks.
- `Services/HardwareService.cs`: shared MIFS/HID access, readback, travel recovery, source profiles and versioned background diagnostics.
- `Services/AdvancedControls.cs`, `ManagerSettings.cs`: XiControl guards, firmware events, monitor and a validated settings catalog.
- `Services/AppLinks.cs`: native app/icon pickers, customization validation and normal-user launch broker. `ForegroundLaunch.cs`: brings an executable or Windows Settings forward after a shortcut launch. `AppearanceOptions.cs`: theme/profile handling. `GlobalShortcuts.cs`: Windows hotkey registration and rollback on conflicts. `CopilotKeyRouter.cs`: resident-only interception of the Windows Copilot chord.
- `Services/OemServiceControl.cs`, `XiaomiBridge.cs`, `OemSession.cs`: reversible service isolation, explicit OEM navigation and scoped session cleanup.
- `Services/ComputerSpecs.cs`: cached Windows inventory. `Services/Preferences.cs`: settings and timestamped local snapshots. `Services/SettingsBackup.cs`: portable settings ZIP export/import. `Services/AppAssets.cs`, `assets/`: editable native and web app icons.
- `www/quick.*`: compact panel. `www/app.js`, `index.html`, `style.css`: categorized manager. `bridge.js`: reply handling, slider coalescing and charge-time estimate.
- `Vendor/XiControl`: copied backend, policies and monitor, GPLv3 license and adaptation notes.
- `tools/`: local build/deployment, validation summaries and passive process sampling.
- `results/`: numbered, append-only run configurations, JSON/CSV evidence and SVG figures. `docs/`: operational and test details.

The popup preloads while hidden at startup. Basic hardware readiness is separate from slow OEM isolation and advanced setup. Trusted-page replies may be sent before NavigationCompleted so early script requests are not dropped. Slow BIOS, battery-capacity and PnP queries run outside the quick-read lock. Confirmed haptic/input updates publish immediately; a version check prevents older diagnostic queries from replacing newer state. Hidden frontend refreshes are skipped. Explicit WebView suspend/resume was removed after it caused disposed-controller errors on reopen. Firmware writes share a transport lock; brightness uses an independent serialized writer with first/latest slider coalescing.

Charge and mode guards reuse XiControl's backend. Manual writes validate and read back the current target. Travel stores its previous care target before requesting 100%; Cancel travel restores that target. Unplug and every resident restart restore the care target. Travel is never resumed from a saved flag. Failed restoration retains recovery data. A configured target is reconciled on power events and a 30-second fallback, with bounded conflict retries. Persistent disagreement is displayed, not represented as success.

## Environment and hardware

Windows x64, .NET 8 Desktop Runtime and WebView2 Runtime are required. Development uses .NET SDK 8.0.425 here, with System.Management 8.0.0, Microsoft.Web.WebView2 1.0.4191.47 and Svg 3.4.7 declared by the project. Existing SDK/packages are under `.test-environment/`; no new installation is needed for this checkout. Node.js and Python 3 standard library are needed only for optional checks and report figures.

Tested device: Xiaomi Book Pro 14 TM2424, BIOS dated 2026-06-17, 16 logical processors, about 31.5 GiB reported RAM, internal 60/120 Hz panel and 200% Windows scaling. Firmware controls require the Xiaomi MIFS/WMI interface; haptics require a recognized HID descriptor. Other models are not certified. Xiaomi kernel interfaces remain installed while OEM UI service isolation is enabled. Intel IGCL telemetry is optional; missing GPU/temperature sources remain unavailable. There is no NPU load, fan RPM or wall-power measurement source, and no accelerator requirement for this app.

## Setup, build and execution

For a second Windows laptop, use the newest `releases/<number>_<timestamp>/PCManager-Setup.exe`. Copy only that EXE to the laptop and double-click it. The installer checks for the x64 .NET 8 Desktop Runtime, offers an all-users install in `C:\Program Files\Xiaomi Revamp\PC Manager` by default, a per-user install under `%LOCALAPPDATA%\Programs\Xiaomi Revamp\PC Manager`, or a custom directory, reversibly disables Xiaomi's original popup service, registers the per-user startup task after administrator approval, and adds **PC Manager** to Start. It stops if OEM isolation fails so that two popups are not installed side by side by accident. The signed-in user must be an administrator who can approve elevation under the same account; entering a different administrator account is deliberately rejected so that startup and recovery files are not installed for the wrong user. Microsoft Edge WebView2 Runtime is also required. If either runtime is missing, install it from Microsoft's official download page and rerun setup. This release is framework-dependent because the available local SDK has no Windows self-contained runtime packs. The setup EXE is unsigned, so Windows may show its normal publisher warning. `PCManager-portable.zip` contains the same executable files for manual use and does not register startup by itself. After extracting it, run `Install PC Manager.ps1 -Scope AllUsers -Destination "C:\Program Files\Xiaomi Revamp\PC Manager"` from PowerShell to install it with the same OEM isolation and startup behavior as the EXE. The installer registers an uninstall entry in Windows Settings and removes only its verified installation directory. The all-users choice shares the program and Start menu entry; each Windows account keeps its own settings, and startup is registered for the account that installs it. Keep `PCManager-source.zip` with any redistributed setup, because the bundled XiControl-derived code is GPLv3.

XiControl does not need to be installed. The Xiaomi PC Manager, Xiaomi Store and XiaoAI executables are optional. The app searches current Program Files installation/version folders and uninstall locations. If one is missing, ordinary hardware controls remain available; opening its shortcut reports that it was not found and offers an executable picker. Settings also lets you set each path explicitly. Driver scanning depends on Xiaomi PC Manager, and the Store link depends on MiAppStore. A normal installation records and disables Xiaomi's original popup service; the installed `Disable Xiaomi service.cmd` reapplies that isolation, and `Restore Xiaomi service.cmd` reverses it. Other Xiaomi models and service layouts remain unverified.

Uninstall from Windows Installed apps or run `Uninstall PC Manager.ps1` in the installation directory. The uninstall dialog has a **Restore Xiaomi's original service and popup** checkbox. Check it to restore the saved OEM service state; leave it unchecked to keep Xiaomi's popup disabled. For unattended removal, `Uninstall PC Manager.ps1 -NoPrompt` keeps it disabled, while `-NoPrompt -RestoreXiaomi` restores it. Before uninstalling, use Settings > **Export backup** and save the ZIP outside app data. It contains `settings.json`, your profile picture, custom icons and artwork. After reinstalling, Settings > **Import backup** validates the file and restarts PC Manager with the restored preferences. The backup contains personal app paths and should remain private. **Save local snapshot** still writes a timestamped JSON copy to `%LOCALAPPDATA%\XiaomiAIManager\settings-snapshots`; full uninstall removes that folder. The uninstaller removes this app's startup task, Start shortcut, uninstall entry, API firewall rule, installed files, LocalAppData preferences/cache/artwork and ProgramData API configuration. Firmware choices and Windows display/input preferences remain at their last selected values; reset them inside the app before uninstall if needed. The uninstaller leaves shared .NET and WebView2 runtimes installed. Windows may retain ordinary execution history such as event logs or Prefetch; those system records are outside this app's installation.

The user profile picture, app links, custom icons, OSD images and CSS live under `%LOCALAPPDATA%\XiaomiAIManager`, not the release folder. Settings > Import asset pack copies a validated set of PNG/ICO/CSS overrides there; see [assets/README.md](assets/README.md). App updates retain this data. The installed native app/tray icon can be overridden by `app.ico` in that folder after a restart; Windows may cache the taskbar icon. The EXE's embedded icon requires rebuilding. The optional CSS can restyle cards and forms, but hardware behavior remains in the program.

After obtaining the source, the user prepares the Windows runtimes, SDK and declared packages. A conventional build is:

```powershell
dotnet restore .\XiaomiAIManager.csproj
dotnet build .\XiaomiAIManager.csproj -c Release
.\bin\Release\net8.0-windows\PCManager.exe --toggle
```

This checkout can rebuild into staging with existing packages, while the daily resident remains running:

```powershell
$env:DOTNET_CLI_HOME = "$PWD/.test-environment/cli-home"
$env:NUGET_PACKAGES = "$PWD/.test-environment/packages"
& ./.test-environment/dotnet/dotnet.exe build XiaomiAIManager.csproj -c Release --artifacts-path .test-environment/artifacts --no-restore -o .test-environment/daily-next
```

`Install daily resident.cmd` is a development deployment command: it changes the startup task to the build in this folder. Use it only when intentionally replacing the installed release for testing. `tools/update-resident.ps1` updates an already registered development resident and stops if its path cannot be verified. Do not overwrite running binaries.

`Open daily manager.cmd` activates the installed release when present and the local development build otherwise. Fixed executable arguments include `--toggle`, `--tray`, `--manager`, `--monitor-small`, `--monitor-medium`, `--monitor-large`, `--cycle-mode`, `--brightness-up`, `--brightness-down`, `--toggle-travel`, `--screen-off`, `--hide` and `--quit`. Later invocations activate the existing resident. No custom shortcut is installed by default; create them in Keyboard. Brightness shortcut steps are five percentage points. Use `--test` for separate local settings and numbered performance OSDs; daily and test residents cannot own the hardware simultaneously.

The startup task targets the installed `PCManager.exe --tray`, allows battery operation, has unlimited runtime and three failure restarts at one-minute intervals. Registration and demand start have been checked; a real reboot/sign-in and long-duration stability are not yet certified. Automatic restart defaults on: an additional one-minute task trigger starts the resident after a clean exit as well as after failures. MultipleInstancesPolicy IgnoreNew avoids repeated starts while it is running. Turn Restart automatically if the app exits off before an intentional long exit. This uses Windows Task Scheduler and no continuously running watchdog process. Both Close actions hide to tray. Sign-in and console-connect triggers have zero configured delay and preload the popup immediately. Windows cannot show this per-user interactive UI before sign-in; hardware/runtime initialization still takes some time.

## Configuration, data and outputs

Daily preferences, native timestamped logs, icon PNGs and WebView2 profile use `%LOCALAPPDATA%/XiaomiAIManager`. XiControl configuration is nested in `settings.json`; API credentials/settings retain their own administrator-protected `%PROGRAMDATA%/XiaomiAIManager/api.json`. API/network features default off. Test data lives beside the test executable in `test-data/` and disables startup registration, keyboard event subscription, API/firewall changes and webhooks.

Ambient-light brightness curves start from XiControl's six default anchor points, not measured calibration data from this laptop. They are stored separately as `XiControl.AutoBrightnessPointsAc` and `XiControl.AutoBrightnessPointsBattery` in `%LOCALAPPDATA%/XiaomiAIManager/settings.json`. When automatic brightness and learning are on, a manual brightness correction is associated with the current light reading and power source after the configurable learning delay, then saved as a curve point. The list is a configuration, not a continuous lux history. The Display page plots points in light-level order and offers a separate reset to defaults for each curve. The currently learned battery curve is specific to this laptop and may look different from the AC defaults. With Settings > Save diagnostic logs on, `native-*.log` in the same data directory records learned changes and adjustments, not every sensor sample. "Notify about upstream XiControl releases" uses the GitHub releases API at most daily when enabled and compares the latest release with bundled component version 0.16.0. It only notifies; it does not download code, update the manager, or compare source files in the supplied folder.

The 5-second visible refresh and 30-second power/charge fallback are polling intervals, not latency guarantees. Enabling automatic display rate immediately applies the configured AC or battery rate and verifies Windows readback; subsequent real source transitions apply the corresponding rate and show the confirmed rate in an OSD. Same-source status events, display-change events, resume and startup do not overwrite a manual rate. Manual rate selection uses the Windows persisted display setting; no repeating refresh-rate enforcement runs. Native request timeout is 30 seconds. A timeout does not cancel an in-flight device operation. Diagnostics cache lasts up to 60 seconds and is invalidated after relevant changes. The monitor samples at 1 Hz while visible, shows 30 seconds by default, and can expand to its three-minute in-memory history. Its large window has an opt-in CSV Log button, off each time it opens. Files go to `%LOCALAPPDATA%\XiaomiAIManager\monitor-logs` in daily mode and the test-data equivalent in test mode. Battery draw is a whole-laptop reading while discharging. On AC, the monitor and Home show only processor-package power; full laptop or wall draw is unavailable without external measurement.

Charging time uses remaining energy: `minutes = 60 * fullWh * max(0, targetPercent - batteryPercent) / 100 / chargingWatts`. Target is 100% during travel, otherwise the requested care/full target. Missing capacity, zero/unknown rate or no charging status produces no numeric estimate. Near-full taper, workload and changing temperature can make this estimate optimistic. Battery flow is net charging/discharging power, not charger rating or wall draw.

**Restore Xiaomi service.cmd** restores the preserved service startup/running state and permissions. **Disable Xiaomi service.cmd** reapplies daily isolation. Recovery evidence and original state live under `%LOCALAPPDATA%/XiaomiAIManager/service-state/CURRENT_USER_SID`; legacy records beside the daily executable migrate without overwriting newer per-user records. Startup-entry backups and development deployment transcripts are under `.test-environment/deployments`. Explicit OEM tools can restore the service. Return to daily isolation with the disable launcher when finished; service restoration can also restore the OEM watchdog and its UI/OSD.

Passive resource measurements and figures are described in the runtime report.

Xiaomi meeting subtitles are hosted through `PcControlCenter.dll` and `SubtitleTranscriptor.dll`, with no verified standalone executable or direct launch contract. Toolbox opens the original quick panel so the user can select Subtitles Translation there. The OEM feature requires Xiaomi account/cloud services, as described by the [Xiaomi PC Manager privacy policy](https://privacy.mi.com/PCManager/zh_CN/). ## OEM sessions and editable assets

Driver updates explicitly use the verified `--scan_driver` flag and restore MiDeviceService on demand. The scanner remains hosted by the official manager; reliable deep navigation on the supplied patch is unconfirmed. Store resolves `C:/Program Files (x86)/MiAppStore/MiAppStore.exe` directly without requesting the manager or service. XiaoAI resolves the newest valid numeric installed version, rather than a fixed version path.

Settings defaults to automatic OEM cleanup. Following an explicit manager launch, a visible landscape main window keeps the session active. Optional Settings > Show original popup alongside ours explicitly requests the inspected `--open_controlcenter` flag and offsets our panel left; that session also recognizes portrait OEM panel windows. It defaults off. Paired popup visibility and cleanup still need physical acceptance. Once that window closes or hides, a six-second grace and installer check precede returning to saved daily isolation and stopping verified OEM background UI. This watcher runs only during an explicit session. MSI processes or uncertain installer images defer cleanup; nonstandard OEM windows can prevent detection. Turn this setting off to leave OEM tools running. Restore Xiaomi service.cmd preserves the recorded original service configuration and clears daily isolation intent.

An application-cloaked OEM window counts as hidden; a window cloaked by the Windows shell remains an active session, so switching virtual desktops does not trigger cleanup. Native close requests did not close the supplied OEM window in testing. The regression suite therefore distinguishes those requests from a controlled window-hide test and from clicking the OEM X button, which still needs physical acceptance. See the runtime report for the observed cleanup result.

To repeat the authorized restart and resource checks with the existing daily installation:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test-restart.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tools/test-resources.ps1 -Seconds 60
```

The first command cleanly quits the resident and waits up to 90 seconds for task recovery. The second captures actual resident preferences through the UI validation bridge, samples the resident and its WebView2 children while hidden and with Small, Medium and Large monitors, then restores the saved monitor size and verifies it through a fresh native capture. These captures briefly exercise and restore UI settings. The wrapper hides the windows afterward. Both preserve fresh numbered results and request administrator elevation. Do not run resource sampling alongside build or hardware validation work. Package watts include all workloads; they cannot determine app-only power consumption.

## Immediate settings, quick controls and independent checks

See [the runtime report](docs/RUNTIME_TEST_REPORT.md) for the current native validation and resource measurements. `Services/SettingsHistory.cs` owns bounded resident-only Undo/Redo; `tools/read-firmware.ps1` reads firmware independently. `tools/test-popup-resources.ps1`, `tools/test-resources.ps1` and `tools/test-manager-resources.ps1` measure hidden, popup, three monitor sizes and manager-visible conditions. They write fresh numbered folders under `results/` and restore the hidden tray state.

Validated controls apply when their value changes, including source profiles, theme colors, popup layout, curve points, icons and app-link order. Text and numeric fields commit on change or leaving the field. Incomplete JSON, invalid values and unfinished shortcut chords remain drafts; errors stay visible. Rapid committed edits are serialized without dropping writes. No Save button is required. Selecting a color preset chooses its accent, background and card colors; subsequent accent edits override the accent, while a background or card edit switches to Custom. Named preset pickers show the rendered colors rather than stale saved custom values. Help puts the default on a separate line.

Manager Undo/Redo buttons and Ctrl+Z/Ctrl+Y retain up to 32 committed edits during the resident session. Changed preferences, source policies, category defaults and common hardware buttons are restored through normal callbacks. Unrelated fields are retained. Text editors keep their ordinary text undo. Brightness dragging uses its independent fast writer and is excluded from this history, as are external app launches, HTTP/API credentials/settings and edits to image file contents. History clears at restart. Firmware/source refusal is reported; a hardware restoration can be partial, so read back the current state after an error. Mode undo refuses when the power source has changed.

The quick panel's Battery care button enables the saved care limit or disables care for persistent 100% charging. The saved limit is chosen in the manager only. Travel charge temporarily overrides enabled care; Cancel travel restores the limit. Every resident start clears saved travel state and reasserts care, including after a crash. Firmware rejection is reported as a charging conflict. A full-charge choice without travel survives startup. The panel displays the saved target and, while charging with valid battery power, an approximate time to that target. This estimate does not model charge tapering.

The Display page uses a two-position 60/120 Hz switch when both rates are supported; other panels retain a list of supported rates. The quick panel's display-rate button shows the confirmed Hz value and cycles the internal panel's supported rates. The same action is available to custom Windows and firmware-key mappings. Fn combinations require actual firmware events; Windows does not expose Fn as a RegisterHotKey modifier. Ordinary S/K input is not intercepted to simulate Fn. The bounded recent-event log is exposed in keyboard diagnostics.

Screen off temporarily sets the current power source's Windows display idle timeout to one second, then restores its saved value after the display wakes, after an unsuccessful request, or at resident startup after a crash. It does not change the sign-in or sleep policies, so Windows may lock the session. The previous explicit `SC_MONITORPOWER` method suspended this laptop's desktop process immediately on AC despite an active Prevent sleep request. With Prevent sleep enabled, the replacement idle-timeout method kept a background process running through more than eight uninterrupted minutes of physical display-off on this TM2424, and restored the original 120-second AC display timeout on wake. This is a finite test on one laptop, not a guarantee for every workload or future Windows power state. On battery, a Modern Standby 506 event can be emitted as soon as the display turns off; Microsoft limits system and execution power requests on DC to five minutes past the sleep timeout. No black-screen overlay is used. The earlier no-lock workaround caused severe wake flickering and is not invoked; its recovery code still restores any old policy journal. The manager retains Maximize/restore and Minimize buttons.

The battery behavior follows Microsoft's [power request lifetime](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-powersetrequest) and [Modern Standby phases](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/prepare-software-for-modern-standby). An S0 506 entry records the display-off standby session; it does not by itself prove the exact second when a desktop process stopped running. The supplied Test 2 heartbeat continued through a 506 event, whereas Tests 1 and 3 had long gaps. The three files and event-log correlation are recorded in `results/154_20260930T002925579_sleep_diagnosis`.

The TM2424 firmware returns `0xE0` for keyboard-backlight GET `0x12`, and no standard Windows HID keyboard-backlight collection was found here. Screen off therefore cannot currently force the keyboard light off or restore its prior Auto state. Fn+K is not emitted by this model's XiControl WMI key channel; physical Fn+S was observed as ordinary S. Windows does not expose Fn as a hotkey modifier. Custom Ctrl+Alt+K and Ctrl+Alt+S actions can be configured in Keyboard without intercepting ordinary typing.

Popup hardware selections keep the panel open. Outside clicks dismiss it, including when Windows refuses foreground activation. A mouse hook runs only while the popup is visible; a tray click that began closing it cannot immediately reopen it. Position is chosen from the screen bounds, so the bottom-right panel stays over an auto-hide taskbar and the clock instead of jumping when the taskbar disappears. The native window fades over about 220 ms when Windows and the app allow animations. The scrollbar stays hidden while wheel scrolling remains available if links exceed the panel height. Manager Settings can disable the fade. Optical smoothness has not been measured.

Quick controls put Screen off, Stay awake, manual Hz and automatic Hz on one display row. Touchpad, touchscreen and Monitor have their own row; custom app links remain above OEM tools. Travel charging shows a compact estimated time to 100% when charging power is available. It restores the care limit when unplugged or when charging reaches 100%; AC reconnection no longer triggers a Travel OSD. Unrelated controls remain available while a firmware write is pending. Writes serialize against confirmed readback so rapid clicks are queued. Disabling persistent Battery care no longer emits the Travel notification. A measured HID write took about 432 ms while browser and native event-loop gaps stayed below 32 ms on the tested laptop.

Read-only hardware diagnosis is available through `tools/read-firmware.ps1` (including raw keyboard-backlight response) and `tools/read-hid.ps1` (HID descriptors). Both require an administrator PowerShell session. `--validate-screenoff` records a skipped result without switching off the display because of the prior wake flicker. `tools/check-quick.mjs` exercises real popup event handlers against a delayed fixture; it does not substitute for native latency testing.

To independently read firmware mode and the charging limit, use an **administrator Windows PowerShell** terminal in this folder. This checker sends only MIFS GET commands, without reading either manager's settings or launching their UI:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/read-firmware.ps1
```

The report includes the raw response, decoded firmware mode and Windows plan. Windows Power mode, Energy saver and EcoQoS are separate controls. Their indicators do not prove a Xiaomi firmware mode. The reader supports the XiControl Classic/Echo dialects; Echo models cannot provide reliable charge-limit data. An installer is available, but device-specific firmware behavior has only been tested on the TM2424. Other Xiaomi laptops are not certified.
